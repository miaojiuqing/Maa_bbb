> 分支：`feat/traditional-chinese-support`
> 目标：让 **繁中客户端（台服/国际服繁体中文）** 能正常使用 MAA_bbb 的自动化流程
> 当前状态：**日常与商店可用；往世乐土前半段可用，其后仍有未解决问题**

## 0. 关于开发方式

本分支大量使用 **AI 编码助手**辅助开发，此处如实说明，避免误解：

- 实际操作、截图与结果验证由使用者完成；AI 负责分析运行日志、定位问题、生成补丁与文档。
- **所有结论以实测日志与截图为准。** 过程中 AI 的推断曾多次被实测推翻，相关教训记录在第 5 节。
- 分支历史经过压缩整理，中间的错误尝试与回退未保留在提交历史中，
  但结论与踩坑记录完整保留在本文档内。
- **建议把本分支当作「一份带实验记录的补丁」来审查，而非成品。**

## 1. 实现方式

繁中客户端与简中客户端存在三类差异，分别处理：

| 差异类型 | 处理手段 | 落点 |
|---|---|---|
| **文字差异**（结算→結算、放弃→放棄） | 为 OCR 节点的 `expected` **追加繁体候选**（追加而非替换） | `繁中兼容.json` 生成逻辑 |
| **界面差异**（按钮文案/位置不同） | 新增识别繁中文字的节点，挂进原候选链 | `繁中助手_规则.json` → `节点补丁` |
| **图片模板差异**（原模板取自简中客户端） | 从实际运行截图裁出繁中模板 | `resource/resource_tw/image/繁中/` |

### 1.1 覆盖包是生成出来的

```
繁中助手_规则.json        （人工维护：用词规则、节点补丁、选项）
        │
        ├─ tw_helper.py  generate_overlay()
        ▼
resource/resource_tw/pipeline/繁中兼容.json   （自动生成，请勿手改）
        │
        ▼
   MaaFramework 加载：resource/base + resource_tw 合并
```

覆盖包**仅在程序启动时加载**，因此每次修改后必须**重启主程序**。

### 1.2 追加式容错

```
原有： expected = ["深层序列"]
追加： expected = ["深层序列", "深[层層]序列", "[深][层層]序列"]
                  ↑ 原有的仍然保留
```

简中环境行为不变，繁中环境能多认几种写法。

## 3. 未解决

### 3.1 【主要】刻印优先级在繁中失效

用户侧已配置优先级（全伤 > 双伤 > 易伤 > 回能 > 双上限），但繁中客户端下不生效。

原因：该优先级选项指向的模板是**简中客户端的小字截图**，例如

```
周常/往世乐土/刻印选择/普通优先级定制/通用增伤/全伤.png        28×19 px
周常/往世乐土/刻印选择/普通优先级定制/能量与生命/双限提升.png    65×22 px
```

繁中客户端写作「全傷害」，字形不同，模板匹配全部落空。

**修复方向**：用繁中客户端实际截图，为这 5 个优先级各裁一张小字模板。

遗留进度弹窗清理、剧情对话跳过、刻印选择、战斗内循环等环节做过实现尝试，
但稳定性不足，**当前版本未启用**（见第 4 节）。

## 5. 关键结论与踩坑记录

### 5.1 MaaFramework 语义

| 结论 | 说明 |
|---|---|
| **`max_hit` 耗尽后节点直接消失** | 不是"拒绝执行"，而是连识别日志都不产生。表现：某界面"其它候选都在试，唯独该点的那个不见了" |
| **`next` 不会自动返回父节点** | 节点 `next` 为空即**流程结束**（界面显示"所有任务都已完成"，实际什么都没做）。要返回上层必须**显式写进去** |
| **候选只在父节点匹配时才展开** | 父节点认不出，`next` 里写再多也不试。每个分叉点都要把可能停住的界面列全 |
| **叶子节点不要给 `next`** | 会提前结束流程或形成死路 |
| **资源层覆盖包改不动部分任务入口节点的 `next`** | 实测「往世乐土-开始任务层」的 `next` 无论怎么覆盖，运行时仍用原生列表。可行解法是新建入口节点并改 `task.entry`，但需配套维护 |

### 5.2 识别

| 结论 | 说明 |
|---|---|
| **超大艺术字 OCR 识别率很低** | 如「挑戰結束」「直接結算」。改用同页普通字号文字，或改图片模板 |
| **白字浅底对比度低 → OCR 读不出** | 如「直接結算」是白字印在浅蓝按钮上；「確定」是深字黄底，可读但不稳定 |
| **模板匹配不受字体影响** | 对"界面长什么样"比 OCR 可靠，且**可直接从 debug 截图裁切**（截图即 1280×720，与管线坐标同空间） |
| **筛选用词要锚定** | `^80$` 可区分「每週限購 0/80」与真正的「80」 |

### 5.3 坐标

| 结论 | 说明 |
|---|---|
| **管线坐标是 1280×720 空间** | 框架会把截图缩放到长边 1280，所有 16:9 分辨率（1920×1080 / 2560×1440 / 4K）共用同一组坐标 |
| **测量外部截图必须先换算** | 2560×1440 的截图坐标需除以 2。曾因忘记换算把点击点算偏 240 像素，表现为"有判定但没行动" |

### 5.4 点击与节奏

| 结论 | 说明 |
|---|---|
| **`LongPress` 反而更容易丢点击** | 仓库原有实测注释已记录该结论。正确做法是「普通点击 + `post_delay`」 |
| **重复点击通常意味着等待不足** | `pre_delay` / `post_delay` 要给够（本次相关节点普遍 1000~4000ms） |
| **关键按钮要能自我重试** | 把自身放进 `next` 首位，点不到下一轮再点；并配固定坐标兜底 |

### 5.5 工程纪律

- **改前先查项目里有没有相关实测注释**，避免重犯已记录过的错误。
- **一次只改一处**，改完重启验证。
- **每次改动后必查**：
  1. `next` / `on_error` 有无指向已删除节点的**悬空引用**（会导致整个资源加载失败）
  2. 叶子节点是否被误加 `next`
- **不要大范围回退**：应先列出待回退节点，逐个确认是否已验证可用；已验证可用的绝不回退。
  本次曾一次性回退 25 个节点，误伤日常修复。
